## What exists

A dark, space-themed learning-path page, behind a login gate, with an insights/account UI in the nav:
- Hero animation (kept unchanged; a small "SSIS to Fabric in 11 weeks" eyebrow line sits above it), 11-week route chart, "where you start" (translation table), freshness check table, 6 phases, stretch missions, guardrails.
- 50 tasks in 6 phases. **Phase 2 is a pilot with 24 lessons** (Learn, Try it, Break it, Prove it, self-test questions, copyable code). Other phases are task lists only.
- **Login gate** (`js/auth.js`): a full-page splash checks the Supabase session, then shows either a login card (email/password) or the app — the app's markup (`header.nav`, `main`, `footer`) is `display:none` by default in CSS and only revealed once JS confirms a session or local-only mode, so there's no flash of content before login. A cosmetic 60-second lockout follows 5 failed sign-in attempts (client-side counter, not enforced server-side). If `config.js` has no URL/key, the gate is skipped entirely and a "local-only mode" banner shows instead — this is a lock screen only: lesson text is still in the page source regardless of login state; the real protection is Row Level Security on the Supabase tables. See README "Login and privacy".
- **Insights pill and account circle** (top-right of the nav, both built in `js/app.js`'s `bindInsights()`): the pill shows the progress ring, percentage, a status dot and "Saved on this device · <IST time>" (collapses to ring+dot only at 900px and narrower); clicking it opens a panel (popover ≥900px, bottom sheet below) with completion/lesson/estimated-hours counts, a thin bar per phase, current phase and next task (`nextItem()` reused, "Open it" reuses `openNext()`), saving status, and an optional start-date control showing "Week N of 11" and a planned-vs-done hours estimate. The account circle (first letter of the signed-in email) is hidden entirely in local-only mode or when signed out; its menu has the email, Export/Import progress (same feature as the footer buttons, triggered via `.click()` on the existing `#exportProgress`/`#importProgress`/`#signOut` buttons rather than duplicating the logic), Sign out, and Sign out and clear this device (wipes `ssis-to-fabric-path-v2`, `-v3`, `-meta` and `ssis-to-fabric-notes-v1` from `localStorage`, then signs out — see "Sign-out is gated by sync state" below for the guard in front of this). Both the pill's panel and the account menu are real dialogs: `Escape` and outside-click close them, focus is trapped while open (Tab-wrap in the panel, arrow keys in the menu) and returns to the opening button on close.
- Times are always shown in IST regardless of the visitor's device time zone (`fmtIST()` in `js/app.js`, built on `Intl.DateTimeFormat` with an explicit `timeZone:"Asia/Kolkata"`; verified against device time zones UTC, America/New_York and Asia/Kolkata all producing the same displayed time). No polling: the pill/panel only update on events (tick/untick/reset/import via `progressChanged()`, note edits via `fireNotesChanged()`, sign-in via `onAuthStateChange`).
- Progress is stored in `localStorage` under key `ssis-to-fabric-path-v3`: `{ v:1, items: { "<id>": [1|0, timestampMs] } }`, one entry per task or lesson id with a per-item last-change timestamp. The legacy flat `ssis-to-fabric-path-v2` (`{ "<id>": 1 }`) is migrated into v3 once, on first load after this update, if v3 doesn't exist yet and v2 does — migrated items all get the same "now" timestamp, and v3 is only written if there was actually something to migrate (an eagerly-written empty v3 would wrongly look "already migrated" and block a v2 write arriving later, e.g. from an older cached tab — this was a real bug, caught by testing, fixed before it shipped). Neither `v2` nor `v3` has been renamed and neither should be. A task with lessons is done when all its lessons are done (derived, never stored). A second key, `ssis-to-fabric-path-meta`, holds `{ lastSavedAt, lastChangeAt, startDate }`. Progress syncs to `public.progress` — see "Sync" below. Notes now sync too — see "Notes" below.
- **Sync** (`js/app.js`, top-level functions, not nested in `bindInsights`): local-first. Every tick/untick/reset/import writes `localStorage` immediately (`persistItems()`), then `scheduleSync()` debounces (~800ms) an upsert of `{v:1, items, meta:{startDate}}` to `public.progress` (`runSync()`), with exponential backoff retry on failure (2s, doubling, capped at 60s, reset to 2s on success). A `localGen`/`savedGen` pair of counters stops a save that was in flight when a newer local edit landed from wrongly marking things "saved" — if generations don't match when a save completes, it immediately reschedules another. `pullAndMerge()` fetches the remote row and merges it into local `items` per-item, latest timestamp wins (`mergeItems()`), then always pushes the (possibly just-merged) result back — this single function handles "first login on a device: upload local progress if remote is empty, otherwise merge" simply by doing nothing in the merge step when there's nothing remote to merge. It runs on sign-in (once per session, guarded by `hasPulledThisSession`), on `visibilitychange` (tab regains focus) and on the `online` event; the `offline` event just sets the "offline" sync state (no timer — it waits for the `online` event to resume). `meta.lastSavedAt` updates on every successful cloud save. The insights pill/panel's `syncStatus()` now reflects four real states (saved/saving/offline/error) instead of always "local only", falling back to the pre-sync "Saved on this device" wording only when there's no `window.APP_AUTH_CLIENT` (local-only mode) at all. `pullAll()` runs both `pullAndMerge()` (progress) and `pullNotes()` (notes) together.
- **Sign-out is gated by sync state** (`guardSignOut()` in `js/app.js`, exposed as `window.APP_SYNC.guardSignOut`, called from both the footer's Sign out button in `js/auth.js` — via `window.APP_AUTH_SIGNOUT`, the raw ungated sign-out, to avoid double-guarding when the account menu triggers the same button — and the account menu's Sign out / Sign out and clear this device): waits (up to 8s) for any in-flight save — progress **and** any dirty notes (`Object.keys(noteSyncInFlight)`) — before deciding anything. If the current state is clean (not dirty, not error, not offline, and `anyNoteUnsynced()` is false), it proceeds immediately. Otherwise it opens `#syncWarn`, a small dialog (`role="alertdialog"`, focus-trapped, `Escape` closes) offering Export progress (opens the existing export dialog, doesn't sign out), Sign out anyway (proceeds despite the risk) or Cancel (does nothing). Clear-device additionally only wipes `localStorage` (`ssis-to-fabric-path-v2`, `-v3`, `-meta`, `ssis-to-fabric-notes-v1`) *after* the guard's proceed decision, never before — confirmed by test that ticking a task, forcing a cloud failure, then choosing Clear-device shows the warning and leaves the ticked task in place until "Sign out anyway" is chosen. Clear-device only ever removes local storage, never the cloud rows, so signing back in afterwards legitimately pulls progress and notes back down — that's intended (it clears the device, not the account), confirmed by the step 5 test suite.
- Export/import progress as JSON from the footer (clipboard, with a select-and-copy fallback; import is validated against known task/lesson ids, unrecognised ids are skipped, valid ones are merged into existing progress rather than replacing it). Also reachable from the account menu, alongside the notes export/import described below.
- No job-search content: it was deliberately removed (see "Pending work" below for what changed).
- It was also published as a claude.ai artifact. The page has no `window.claude` calls, so it runs anywhere (though the login gate now needs a reachable Supabase project, or `config.js` left empty, to behave sensibly).
- **Notes** (`js/app.js`, top-level storage/sync functions plus `bindNotes()` for the UI): a Markdown note per phase (`p0`…`p5`), per lesson (`lesson:<id>`, phase 2 only so far) and one global scratchpad (`scratch`) — the only valid scope patterns, checked by `isValidScope()` on both import and cloud pull, so a malformed scope string never reaches the UI. Stored in `localStorage` under `ssis-to-fabric-notes-v1`: `{v:1, notes:{ "<scope>": {body, localUpdatedAt, serverUpdatedAt, dirty} }}`, each scope with its own dirty flag and debounce/retry state so one scope's failure doesn't block another's. Every keystroke in the textarea writes `localStorage` immediately (`setNoteBody` → no extra editor-level debounce — see the bug this replaced, below) and schedules a ~800ms-debounced per-scope upsert (or, for an empty body, a delete) to `public.notes`, with the same exponential-backoff retry pattern as progress sync. `pullNotes()` runs alongside `pullAndMerge()` inside `pullAll()` on sign-in/focus/online: a clean (non-dirty) local scope silently adopts a newer remote row; a **dirty** local scope with a newer remote row is a genuine conflict — neither side is auto-overwritten, `noteConflicts[scope]` is set, and `openConflictDialog()` shows both versions (with IST timestamps) and three explicit choices — Keep mine, Use theirs, Copy mine to clipboard (which copies, then adopts theirs) — deliberately with **no** Escape-to-dismiss.
- **Notes UI**: a **Notes** button sits beside (not inside) each phase's accordion-toggle button in a `.ph-head-row` wrapper — two sibling buttons, not a button-in-a-button — so clicking it never triggers the accordion; each phase-2 lesson has its own "Add note" button; the nav has a "Notes" link for the scratchpad; all three carry a `.notes-dot` that lights up once that scope has a note (`updateNoteDots()`, refreshed on every `onNotesChanged` firing). All of them open the same drawer (`bindNotes()`'s `openNotes()`): a right-hand panel ≥900px, a bottom sheet below that, `role="dialog"`, focus-trapped, closes on `Escape` or an outside click, returns focus to the opener. The editor has Edit/Preview tabs; **`renderMarkdown()`/`inlineMd()` escape the raw text first, then build tags only around already-escaped text**, so a note body is never interpreted as live HTML — headings, `-`/`*`/numbered lists, `**bold**`/`*italic*`/`` `code` ``, fenced ` ``` ` blocks, `#tags` (rendered as chips, clickable to filter the scratchpad) and `[text](url)` links, with the link regex restricted to `https?://`/`mailto:` so a `javascript:` URL never becomes a real `<a>` — confirmed against both a raw `<img onerror>` payload and a `[x](javascript:...)` link rendering as inert text with no dialog firing. A 50,000-character counter matches the DB's `CHECK` constraint. A small **"i" info button** at the top-right of the drawer opens a popover with the Markdown reference (added after the original design, which put that reference as permanent placeholder text in the editor — moved behind the icon on request) — closes on `Escape` (checked before the drawer's own `Escape`-closes-drawer handling) or an outside click. `beforeunload` warns while any note (not just the open one) has an unsynced change or in-flight save. Ticking a phase-2 lesson can trigger a dismissible two-line reflection prompt that appends a dated IST line to that lesson's note if filled in. Export all notes as grouped Markdown or as JSON (`Blob` download); JSON import validates scopes before writing. The scratchpad additionally has debounced search and tag-filter chips. All of this is reachable from the account menu alongside progress export/import.
  - **Real bug found and fixed in the step 5 test pass**: the conflict dialog (`#conflictDialog`) lives outside `#notesDrawer` in the DOM (it's a separate top-level dialog). The drawer's own "outside click closes it" listener (`onNotesOutside`, a capturing `document` listener) didn't know about it, so physically clicking any conflict-dialog button (Keep mine / Use theirs / Copy mine) was treated as a click *outside* the notes drawer — closing the drawer (`notesOpen=false`) during the event's capture phase, *before* the conflict button's own click handler ran. The conflict resolution itself still completed correctly (localStorage ended up right), but `finish()`'s `if(currentNoteScope===scope&&notesOpen)` guard then saw `notesOpen===false` and skipped refreshing the editor, so the textarea kept showing the stale pre-resolution text indefinitely — a real, user-visible bug, not just a test artifact (confirmed by polling: the underlying data was already correct within one tick, but the visible textarea never changed across 1.5s of polling). Same root cause also meant `Escape` while the conflict dialog was open would incorrectly close the notes drawer behind it, even though the conflict dialog itself intentionally ignores `Escape`. Fixed by making `onNotesOutside` and `onNotesKey` both check `#conflictDialog`'s visibility first and stand down when it's open (`js/app.js`, `onNotesKey`/`onNotesOutside` inside `bindNotes()`). Caught by a Playwright test that used a **physical** `page.click()` on the conflict dialog's button rather than invoking the handler directly — invoking `el.onclick()` via `page.evaluate` masked the bug entirely, since that bypasses the DOM event's capture phase; worth remembering for any future dialog-nesting test.

## Design decisions worth keeping

- Layer colours mean something: bronze = foundations, silver = core engineering, gold = production and proof. Phase markers are planets; the glowing probe follows scroll.
- Performance work is done: stars are pre-rendered tiles animated by CSS, scroll work is event-driven, no `backdrop-filter`, `content-visibility:auto` on lower sections, lessons lazy-rendered. Original baseline (headless Chromium, 1890px, before login/sync/notes existed): idle JS about 6 ms/s, scroll JS about 9 ms/s, about 1,550 DOM nodes. Re-measured in the step 5 test pass, same method, now with the full login/sync/notes UI present: idle JS about 1.5 ms/s (lower, not higher — nothing runs per-frame at idle), scroll JS about 17–20 ms/s (up from the ~9 ms/s baseline — the extra listeners and dialogs the notes/insights UI added cost something on scroll, though still well short of anything visibly janky in testing), about 1,611 DOM nodes (up from ~1,550, expected given the new drawer/dialogs). Worth a closer profiling pass if scroll ever feels heavy on a real low-end phone (see "Pending work" E). Do not reintroduce per-frame full-canvas redraws or a root CSS variable updated on scroll.
- `body{isolation:isolate}` is required. Without it the `#cosmos` layer paints under the body background and the sides look plain black (this was a real bug).
- Respects `prefers-reduced-motion` (CSS kills animations, JS avoids loops).
- Copy style: plain sentences, no em dashes, UK spelling in prose, no filler.

## How to test locally
- Syntax: `node --check` each file in `js/` directly (they're no longer inline, so there's nothing to extract).
- Behaviour: Playwright against a local server that sends the same headers as `netlify.toml` (a bare `file://` open won't enforce the CSP, so it can hide a real violation). Useful checks: no console errors (ignore the blocked Google Fonts request in sandboxes), `document.documentElement.scrollWidth === viewport width` at both 390px and 1890px, open a lesson, tick it, confirm the task becomes done and progress survives a reload.
- Mock `window.supabase.createClient` (intercept the pinned jsDelivr URL and serve a stand-in) for login/sync/notes tests, backed by a small fake `progress`/`notes` REST endpoint so two separate Playwright browser contexts can genuinely converge, not just each pass in isolation. See "Pending work" B's step 5 entry above for the full list of scenarios this should cover.
- IST timestamps: run the same scenario under `timezone_id` `UTC`, `America/New_York` and `Asia/Kolkata` and confirm the displayed time string is identical in all three.
- XSS in notes: feed `<img onerror>`, a `<script>` tag and a `javascript:` link into a note body and confirm none become live markup — check the rendered `innerHTML`, not just the absence of a fired `alert`.
- Measure JS cost by wrapping `requestAnimationFrame` and summing callback time while idling and scrolling — see the current numbers under "Design decisions" above.
